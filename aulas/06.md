<h2 id="topico1">1. Criando o Model SiteContato</h2>

- **Models**:
    - são as classes que representam os objetos da nossa aplicação.
    - através delas podemos trazer para nossos códigos os benefícios da programação orientada a objetos - entre eles, a reutilização de código.
- criando a Model:
    - abrir o terminal, no diretório do projeto app_super_gestao.
    - executar o comando `php artisan make:model SiteContato -m`.
        - **importante**: os nomes dos modelos devem ser escritos sempre no singular.
        - SiteContato vai representar cada um dos contatos feitos através do site; vamos criar uma Classe que será instanciada, se transformando em objeto e contendo os atributos do Contato, para que mais adiante possa ser persistido no BD.
        - o `-m` automaticamente cria o Modelo e uma Migration.
- o modelo será encontrado em app > Models > SiteContato.php, com o conteúdo:

~~~php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class SiteContato extends Model
{
    //
}
~~~

<h2 id="topico2">2. Implementando a migration SiteContato</h2>

- `Migration`:
    - nos permite modelar o Banco de Dados da aplicação através do próprio php; ou seja, não vamos precisar utilizar o SQL Para definição das tabelas das aplicações (podemos escrever as migrações através do php e, sempre que necessário, usar migrações para construir ou reconstruir as tabelas no BD).
    - é um ótimo recurso, principalmente quando estamos trabalhando em projetos que envolvem vários programadores: os script responsáveis pelas criações e pelas alterações dessas tabelas se tornam parte do projeto, podendo inclusive ser versionados, o que facilita a aplicação das alterações em BDs por parte dos demais programadores.
    - se o sistema depender de um processo de implantação em cada um dos clientes, as migrations ajudarão a colocar o BD da aplicação de pé, de forma mais prática e segura.

- em `database` > `migrations`, acessar a migration `create_site_contatos_table.php`.
    - as Models são sempre criadas no singular (pois representam um objeto daquele tipo), enquanto as tabelas/Migrations são sempre no plural (o próprio Laravel inclui o "s" no final da nomenclatura para indicar que vamos criar uma "coleção" de site_contatos - uma tabela com vários registros).

~~~php
<?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    /**
     * Run the migrations.
     */
    public function up(): void
    {
        Schema::create('site_contatos', function (Blueprint $table) {
        // cria uma tabela (Schema) chamada 'site_contatos', com os atributos:
            $table->id(); // identificador único
            $table->timestamps(); 
            /* adiciona à tabela duas colunas: uma para a data 
            de criação de registro e outra para o momento de
            atualização do registro */
        });
    }

    /**
     * Reverse the migrations.
     */
    public function down(): void
    {
        // permite reverter a migration
        // remove a tabela
        Schema::dropIfExists('site_contatos');
    }
};
~~~

- em `https://laravel.com/`, acessar `Docs` > `Databases and Migrations` > `Database: Migrations` > `Creating Columns`, há a seção **Available Column Types**, onde há os tipos de colunas que podemos implementar nas migrações.
    - exemplo: para criar a coluna "nome", utilizaremos 'varchar', com base no comando `$table->string('name', length: 100);` que consta na documentação.
- portanto, na Migration `create_site_contatos_table.php`:

~~~php
public function up(): void
    {
        Schema::create('site_contatos', function (Blueprint $table) {
            $table->id();
            $table->timestamps();
            $table->string('nome', length: 50);
            $table->string('telefone', length: 20);
            $table->string('email', length: 80);
            $table->integer('motivo_contato');
            $table->text('mensagem');
        });
    }
~~~

<h2 id="topico3">3. Configurando o BD SQLite e executando as migrations</h2>

- `SQLite`:
    - é um banco de dados SQL relacional embutido; com ele, não precisamos realizar a instalação de um SGBD como MySQL, PostgreSQL ou SQL Server.
    - é baseado em um arquivo de texto cujos dados são escritos diretamente dentro dele.
    - pode ser utilizado em pequenos projetos, onde não existe a necessidade de escalabilidade ou segurança; mas o ideal é utilizá-lo apenas nas atividades de desenvolvimento e testes.

- para preparar o SQLite dentro do projeto, precisamos analisar o arquivo `database.php`, localizado dentro do diretório config, na raiz do projeto.
    - esse arquivo guarda as conexões com os bancos de dados.
    - há connections pré-estabelecidas com os BDs sqlite, mysql, sqlsrv e pgsql.

~~~php
'connections' => [

        'sqlite' => [
            'driver' => 'sqlite',
            'url' => env('DB_URL'),
            'database' => env('DB_DATABASE', database_path('database.sqlite')),
            'prefix' => '',
            'foreign_key_constraints' => env('DB_FOREIGN_KEYS', true),
            'busy_timeout' => null,
            'journal_mode' => null,
            'synchronous' => null,
            'transaction_mode' => 'DEFERRED',
        ],
        // ...
]
~~~

- o `método env` verifica a existência das variáveis de ambiente, e as utiliza na composição das strings de conexão.

- essas **variáveis de ambiente**, por sua vez, são determinadas dentro do arquivo `.env`, na raiz do projeto:

~~~php
DB_CONNECTION=sqlite
# DB_HOST=127.0.0.1
# DB_PORT=3306
# DB_DATABASE=laravel
# DB_USERNAME=root
# DB_PASSWORD=
~~~

- remover `# DB_DATABASE=laravel` do arquivo **.env**, para que, quando executarmos **database.php**, o comando `'database' => env('DB_DATABASE', database_path('database.sqlite'))` verifique que esta variável **DB_DATABASE** não existe, e pesquise em **database_path** (no diretório database) um arquivo de texto chamado `database.sqlite` (que devemos criar nesse momento - no meu caso, já estava criado).

- no console, executar o comando `php artisan migrate`; esse comando executa todas as migrações contidas no projeto.

        - reiniciamos o serviço novamente com `sudo systemctl restart mysql`.
    - para fazer com que o serviço seja automaticamente iniciado, no boot do sistema operacional: `sudo systemctl enable mysql`. E para desabilitar, `sudo systemctl disable mysql`.

- é o client visual para a utilização do SGBD MySQL.
- executar o comando `sudo apt install mysql-workbench-community`.

<h2 id="topico9">9. Migration - Adicionando campos a uma tabela</h2>

- há várias formas de adicionar novas colunas dentro de tabelas que já foram criadas no BD.
    - 1) pelo Workbench, através de `alter table fornecedores add ...` - porém causará uma distorção em relação à tabela no BD e à migration responsável pela criação desta tabela.
    - 2) através da migration responsável pela criação da tabela (em `create_fornecedores_table.php`), e depois reprocessar nossas migrations - veremos adiante.
    - 3) criando uma `nova migration` que conterá as instruções apenas para inclusão das novas colunas - é o que faremos nessa aula (um desenvolvimento incremental no BD).

- criando uma nova migration para adicionar colunas à tabela Fornecedores:
    - executar o comando `php artisan make:migration alter_fornecedores_novas_colunas`.
    - em migrations > `alter_fornecedores_novas_colunas.php`:

~~~php
public function up(): void
    {
        Schema::table('fornecedores', function (Blueprint $table) {
            $table->string('uf', length: 2);
            $table->string('email', length: 150);
        });
    }

// table no lugar do create!!!
~~~

- executar o comando `php artisan migrate`.

<h2 id="topico10">10. Migration - Métodos up e down</h2>

### a) Método up():

- tudo que está contido dentro do método up() é executado quando excutamos o comando `php artisan migrate`.
- é responsável por executar migração / modificação no BD.

### b) Método down():

- é responsável por reverter tudo aquilo que foi criado no método up().
- o que for criado dentro de um método up de uma migration precisa ser desfeito dentro do método down() dessa respectiva migration, para que seja possível utilizar o recurso de rollback das migrações.

> Na última aula, criamos uma migração para adicionar duas novas colunas a uma tabela; então no método down() implementaremos a lógica que vai remover essas duas colunas que foram adicionadas.

- portanto, em `alter_fornecedores_novas_colunas.php`:

~~~php
public function down(): void
    {
        Schema::table('fornecedores', function (Blueprint $table) {
            $table->dropColumn('uf');
            $table->dropColumn('email');
        });
    }
~~~

- também podemos passar um array de colunas, da seguinte forma:

~~~php
public function down(): void
    {
        Schema::table('fornecedores', function (Blueprint $table) {
            $table->dropColumn(['uf','email']);
        });
    }
~~~

- para executar a operação de rollback, executar o comando `php artisan migrate:rollback`.
    - a execução do método down() acontece da migração mais atual para a mais antiga (ao contrário do up()).

- para verificar que realmente a migration ocorreu, e que as colunas foram excluídas, executar no Workbench: 

~~~sql
describe fornecedores;

select * from migrations;
~~~

- podemos determinar quantos passos de rollback queremos dar, através da instrução: `php artisan migrate:rollback --step=2`.
    - nesse caso, executa o método down() da migration que criava a tabela fornecedores e da que criava a tabela site_contatos.

> Para criar tudo de novo, executar `php artisan migrate`.

<h2 id="topico11">11. Migration - Modificadores Nullable e Default</h2>

- `Modificador Nullable`: permite que colunas recebam valores nulos/vazios.
- `Modificador Default`: permite a inclusão de um valor default para uma determinada coluna, caso o valor não seja passado no momento da inserção do registro.

- criaremos uma nova migration, para a criação de uma nova tabela, chamada "Produtos": `php artisan make:migration create_produtos_table`.

- na `Migration create_produtos_table`:

~~~php
public function up(): void
{
    Schema::create('produtos', function (Blueprint $table) {
        $table->id();
        $table->string('nome', length:100);
        $table->text('descricao')->nullable();
        $table->integer('peso')->nullable();
        $table->float('preco_venda', 8, 2)->default(0.01);
        $table->integer('estoque_minimo')->default(1);
        $table->integer('estoque_maximo')->default(1);
        $table->timestamps();
    });
}
~~~

- executar `php artisan migrate`.

<h2 id="topico12">12. Migration - Adicionando chaves estrangeiras (Relacionamento um para um)</h2>

- estabelecer esses relacionamentos será muito importante posteriormente pata o Mapeamento Objeto Relacional (quando iniciaremos as tratativas com o **Eloquent ORM** do Laravel).
- nessa aula estabeleceremos o relacionamento entre as tabelas `produtos` e `produtos_detalhes` (relacionamento do tipo 1:1).

### a) Criando a tabela `produtos_detalhes`:

- a ideia é que cada produto contido em `produtos` tenha apenas um único relacionamento com um registro da tabela `produtos_detalhes.`.
- na linha de comando: `php artisan make:migration create_produtos_detalhes_table`.

### b) Na Migration `create_produtos_detalhes_table`:

- precisamos fazer com que a **chave primária** de uma das tabelas do relacionamento viaje para a outra tabela, onde será recebida como **chave estrangeira**.
    - por convenção, em um relacionamento 1:1, o indicado é que a chave primária da tabela mais forte do relacionamento (a que tem mais impacto pro negócio) viaje como chave estrangeira para a tabela mais fraca do relacionamento (a que tem menos impacto/menos importância para o negócio).
    - nesse caso, o id da tabela produtos viajará para a tabela produto_detalhes, onde será chave estrangeira, e a coluna que receberá esse id se chamará `produto_id`.
        - por convenção, quando definimos uma chave estrangeira, usamos o "singular do nome da tabela + underline + id", ou seja: produto_id (omitimos o S).
        - é fundamental que a coluna da tabela que vai receber a chave estrangeira tenha o mesmo tipo da chave primária. Nesse caso, é do tipo "bigint unsigned" (**unsigned** = não aceita valores negativos // **signed** = aceita valores negativos).
        - o **unique()** garante que em produto_id não possa incluir valores repetidos (se não incluisse unique, seria relacionamento 1:N).

~~~php
public function up(): void
{
    Schema::create('produtos_detalhes', function (Blueprint $table) {
        //colunas da tabela produtos_detalhes
        $table->id();
        $table->unsignedBigInteger('produto_id');
        $table->float('comprimento', 8, 2);
        $table->float('largura', 8, 2);
        $table->float('altura', 8, 2);
        $table->timestamps();

        // constraint de relacionamento 1:1
        $table->foreign('produto_id')->references('id')->on('produtos');
        $table->unique('produto_id'); 
        // unique() garante que seja 1:1, sem valores repetidos
    })
}
~~~

- executar o comando `php artisan migrate`.

<h2 id="topico13">13. Migration - Adicionando chaves estrangeiras (Relacionamento um para muitos)</h2>

- na tabela `produtos`, não determinamos qual a unidade de medida para **peso**, assim como para os atributos **altura**, **largura** e **comprimento** da tabela `produto_detalhes`.
- portanto, criaremos a `TABELA UNIDADES`, onde teremos uma relação de unidades de medida e peso, as quais serão encaminhadas para as batelas produtos e produtos_detalhes (muitos produtos podem estar relacionados a uma unidade - relacionamento 1:N, o mais comum de encontrarmos no dia a dia).
- nesse caso, **não utilizaremos o índice `unique`**, permitindo que na tabela para onde viaja a chave estrangeira esse valor se repita quantas vezes for necessário.
- começar criando uma nova migration: `php artisan make:migration create_unidades_table`
- em `create_unidades_table`:
    - no relacionamento 1:N, a chave primária da tabela de cardinalidade 1 viaja como chave estrangeira para as tabelas de cardinalidade N (ou seja, o id da tabela `unidades` vai viajar como chave estrangeira para `produtos` e `produto_detalhes`).

~~~php
public function up(): void
{
    Schema::create('unidades', function (Blueprint $table) {
        $table->id();
        $table->string('unidade', length: 5); // cm, mm, kg
        $table->string('descricao', length: 30); // para detalhar qual a unidade de medida
        $table->timestamps();
    });

    // adicionar o relacionamento com a tabela produtos
    Schema::table('produtos',function(Blueprint $table) {
        $table->unsignedBigInteger('unidade_id');
        $table->foreign('unidade_id')->references('id')->on('unidades');
    });

    // adicionar o relacionamento com a tabela produto_detalhes
    Schema::table('produto_detalhes', function(Blueprint $table){
        $table->unsignedBigInteger('unidade_id');
        $table->foreign('unidade_id')->references('id')->on('unidades');
    });
}
~~~

- já no método down(), precisamos fazer a reversão seguindo a ordem lógica: antes de excluir a tabela unidades, precisamos remover as chaves estrangeiras, senão teremos erros na tentativa de exclusão da tabela!
    - o nome da foreign key é criada pelo Laravel seguindo algumas convenções: `[table]_[coluna onde a fk foi atribuída]_foreign`.

~~~php
public function down(): void
{
    // remover o relacionamento com a tabela produto_detalhes
    Schema::table('produto_detalhes', function(Blueprint $table){
        // remover a foreign key
        $table->dropForeign('produto_detalhes_unidade_id_foreign');
        // remover a coluna unidade_id
        $table->dropColumn('unidade_id');
        
    });

    // remover o relacionamento com a tabela produtos
    Schema::table('produtos',function(Blueprint $table) {
        // remover a foreign key
        $table->dropForeign('produtos_unidade_id_foreign');
        // remover a coluna unidade_id
        $table->dropColumn('unidade_id');
    });

    // remover a tabela 'unidades'
    Schema::dropIfExists('unidades');
}
~~~

- executar `php artisan migrate`.

<h2 id="topico14">14. Migration - Adicionando chaves estrangeiras (Relacionamento muitos para muitos)</h2>

- esse tipo de relacionamento sempre envolve uma terceira tabela.
- nesse caso, criaremos a `tabela filiais`, e um **relacionamento de muitos para muitos** entre `produtos` e `filiais`, de modo que o mesmo produto pode estar em várias filiais e uma filial pode ser utilizada em vários produtos.    
    - logo, precisaremos criar uma terceira tabela (chamada `produto_filiais`), que vai armazenar como chaves estrangeiras, as chaves primárias de cada uma das tabelas envolvidas no relacionamento de muitos para muitos.
    - na prática, vamos criar dois relacionamentos de 1:N com `produto_filiais`, essa terceira tabela auxiliar (teremos `produtos` em relação 1:N com `produto_filiais` e `filiais` em relação 1:N com `produto_filiais`).
- também faremos um **refacture** na tabela `produtos`, agora que temos atributos que podem variar de acordo com a filial (precisarão migrar para a tabela auxiliar).

> executar `php artisan make:migration ajuste_produtos_filiais`.

- criar a tabela filiais.
- criando a tabela produto_filiais (auxiliar).
    - incluir as colunas dos relacionamentos.
    - preco_venda, estoque_minimo e estoque_maximo, da `tabela produtos`, dependem do relacionamento entre produto e filial, podendo variar de uma filial para outra; portanto, devemos migrar essas 3 colunas para essa tabela auxiliar `produto_filiais`.

- método up() da Migration:

~~~php
public function up(): void
    {
        //criando a tabela filiais
        Schema::create('filiais', function(Blueprint $table){
            $table->id();
            $table->string('filial', length: 30);
            $table->timestamps();
        });

        //criando a tabela produto_filiais (auxiliar)
        Schema::create('produto_filiais', function(Blueprint $table){
            $table->id();
            $table->timestamps();    
            // colunas dos relacionamentos
            $table->unsignedBigInteger('filial_id');
            $table->unsignedBigInteger('produto_id');
            // migrando colunas da tabela produtos
            $table->decimal('preco_venda', 8, 2);
            $table->integer('estoque_minimo');
            $table->integer('estoque_maximo');
            // estabelecendo as foreign keys (constraints)
            $table->foreign('filial_id')->references('id')->on('filiais');
            $table->foreign('produto_id')->references('id')->on('produtos');

        });

        // removendo as colunas da tabela produtos
        Schema::table('produtos', function(Blueprint $table){
            $table->dropColumn(['preco_venda', 'estoque_minimo', 'estoque_maximo']);
        });
    }
~~~

- no método down():

~~~php
public function down(): void
    {
        // adocionando as colunas da tabela produtos
        Schema::table('produtos', function(Blueprint $table){
            $table->decimal('preco_venda', 8, 2);
            $table->integer('estoque_minimo');
            $table->integer('estoque_maximo');
        });

        //removendo a tabela produto_filiais (auxiliar)
        Schema::dropIfExists('produto_filiais');

        //removendo a tabela produto_filiais (auxiliar)
        Schema::dropIfExists('filiais');
    }
~~~

- executar `php artisan migrate`.

<h2 id="topico15">15. Migration - Modificador After</h2>

- é um modificador de coluna que permite que novas colunas sejam inseridas em pontoas específicos de uma tabela pré-existente.
- podemos indicar que a nova coluna deve ser criada (after) uma coluna pré-existente.
- novas colunas são sempre adicionadas à direita, ou seja, no final da relação de colunas de uma tabela.
    - se quisermos posicionar as colunas em uma posição **específica** da tabela, seja por preferência, estética ou padronização, utilizamos o `Modificador After`.

> Criaremos uma nova coluna, chamada `site`, na tabela `Fornecedores`, e através do **modificador after**, a posicionaremos à direita da coluna `nome`.

- executar `php artisan make:migration alter_fornecedores_nova_coluna_site_com_after` e, na migration:

~~~php
public function up(): void
{
    Schema::table('fornecedores', function(Blueprint $table){
        $table->string('site', length: 150)->after('nome')->nullable();
    });
}

public function down(): void
{
    Schema::table('fornecedores', function(Blueprint $table){
        $table->dropColumn('site');
    });
}
~~~

- executar `php artisan migrate`.

<h2 id="topico16">16. Migration - Comandos Status, Reset, Refresh e Fresh</h2>

### a) Comando Status:

- é um atalho para listagem das migrations que já foram executadas.
- comando `php artisan migrate:status`.
- retorna o mesmpo resultado de quando executamos `select * from migrations;` no Workbench.
    - a diferença é que o comando Status permite verificar se a Migration já foi executada ou se está pendente.

### b) Comando Reset:

- reverte todas as migrações do BD (exerce os métodos down/rollback de todas as migrations), da mais atual para a mais antiga.
- comando `php artisan migrate:reset`.

### c) Comando Refresh:

- reverte todas as migrações do BD (exerce os métodos down/rollback de todas as migrations), e na sequência automaticamente executa o método migrate (recria o BD) para recriar os objetos.
- comando `php artisan migrate:refresh`.

### d) Comando Fresh:

- parecido com o Refresh, mas ao invés de executar o método down() de cada uma das migrations, ele dropa todos os objetos do BD sem nenhum tipo de rollback, e na sequência ele executa o comando migrate para recriar os objetos.
- comando `php artisan migrate:fresh`.

<h2 id="topico17">17. Entendendo o Eloquent ORM</h2>

- `Eloquent` é o nome do ORM (Object Relational Mapper ou Mapeamento Objeto Relacional) nativo do framework Laravel.
- é uma técnica para aproximar o paradigma de desenvolvimento de aplicações orientadas a objetos com um banco de dados relacional.
- as bibliotecas ou frameworks ORM definem como os dados serão mapeados entre os dois ambientes: BD relacional e uma aplicação orientada a objetos.
- através desse mapeamento, a biblioteca ou framework ORM fornece recursos para gravação, atualização, seleção e remoção de registros, o que diminui significativamente o tempo de desenvolvimento de uma aplicação.
- o ORM é um método independente de linguagem de programação, e atualmente dois padrões se destacam no mercado: 
    - `Data Mapper`.
    - `Active Record`: é o padrão seguido pelo Eloquent.
- agora nossos modelos (Models) passarão a interagir com o banco de dados através do Mapeamento Objeto Relacional.

- é uma ferramenta nativa do framework Laravel.
- é um console interativo que possibilita o acesso às classes do projeto através da linha de comando.

> No terminal, utilizar o comando: `php artisan tinker`.

~~~shell

New PHP manual is available (latest: 3.1.1). Update with `doc --update-manual`
> 
~~~

- por que utilizar um console interativo para acessar as classes do projeto?
    - através do tinker nós podemos manipular as classes relativas aos Models do projeto.
    - podemos, por exemplo, manipular as classes relativas aos Models do projeto; podemos instanciar essas classes e executar os métodos dos objetos instanciados e estéticos também.
    - através dele também podemos testar o Mapeamento Objeto Relacional.
    - em um ambiente sem o Tinker seria necessário realizar os testes dos Models e entre eles e o BD diretamente na aplicação, através da construção précia de uma interface web ou de um script para esse propósito.
    - ou seja, o Tinker é um **atalho**, um shell do php que nos permite testar os Models e o Eloquent ORM do Laravel.

<h2 id="topico20">20. Eloquent - Ajustando o nome da tabela no Model para um correto ORM</h2>

- o que o Eloquent/Laravel faz para **identificar automaticamente o nome da tabela no banco** é: 
    - 1. separar as palavras do nome da classe de acordo com o padrão CamelCase, e incluindo o underline.
    - 2. colocar as palavras em caixa baixa.
    - 3. incluir um S no final.

- caso o nome do modelo não corresponda com o nome da tabela no BD (como no caso da Model Fornecedor e da tabela 'fornecedor**e**s'):
    - quando criamos modelos que estendem de Model, nós temos no contexto da nossa classe o `atributo protected $table`, que permite definir qual o nome da tabela destino daquele objeto.
    - esse atributo se sobrepõs à nomeação automática do Eloquent.
    - exemplo:

~~~php
<?php
namespace App\Models;
use Illuminate\Database\Eloquent\Model;
class Fornecedor extends Model
{
    //
    protected $table = 'fornecedores';
}
~~~

- usar a instrução `quit` para sair do Tinker, e acessá-lo novamente com `php artisan tinker`.
- na linha de comando, inserir:


<h2 id="topico21">21. Eloquent - Inserindo registros com Create e Fillable</h2>

- `Create` é um método estático herdado da classe Model, que permite, através de uma sintaxe mais enxuta, fazer a inserção de registros no BD.
    - o método estático, diferente do método convencional, não depende da instância do objeto; podemos apenas chamar o método passando os parâmetros, se for o caso, sem que haja a instância desse objeto antes.
    - na linha de comando, executar `\App\Models\Fornecedor::create([array associativo com atributos e valores]);`; exemplo:

~~~shell
\App\Models\Fornecedor::create(['nome'=>'Fornecedor ABC', 'site'=>'fornecedorabc.com.br','uf'=>'RJ','email'=>'contato@fornecedorabc.com.br']);
~~~

- esse comando retornará um erro, informando que a coluna "nome" não está na `opção Fillable`: significa que antes de usar o método Create, precisamos ter certeza de que os parâmetros passados no array associativo estão presentes na variável Fillable do nosso modelo.
- portanto, em `\App\Models\Fornecedor.php`:

~~~php
<?php
namespace App\Models;
use Illuminate\Database\Eloquent\Model;
class Fornecedor extends Model
{
    //
    protected $table = 'fornecedores';
    protected $fillable = ['nome', 'site', 'uf', 'email'];
}
~~~ 

- reiniciar o Tinker e executar novamente:

~~~shell
\App\Models\Fornecedor::create(['nome'=>'Fornecedor ABC', 'site'=>'fornecedorabc.com.br','uf'=>'RJ','email'=>'contato@fornecedorabc.com.br']);
~~~

<h2 id="topico24">24. Eloquent - Selecionando registros com where()</h2>

- é um Construtor; permite que diversos outros métodos sejam utilizados em conjunto para construir a query adequada para a seleção dos registros no banco.
- utilizaremos a tabela site_contatos, e por enquanto o nosso foco está em fazer comparações simples, usando **operadores lógicos de comparação** (>, >=, <. <=, <>, ==, like).

~~~shell
use \App\Models\SiteContato;
# $contatos = SiteContato::where('nome da coluna', 'operador de comparação', 'valor');
$contatos = SiteContato::where('id', '>', 1);
~~~

- o Tinker retorna um `Builder`, ou seja, ainda estamos construindo nossa consulta; para que a consulta retorne uma Collection, precisamos utulizat o **método get()** na sequência, como em `$contatos = SiteContato::where('id', '>', 1)->get();`.

- caso precisemos fazer a seção de parâmetros usando o **igual**, basta o0mitir o segundo parâmetro, como em `$contatos = SiteContato::where('nome', 'Maria')->get();`.

- já o **like** é utilizado para fazer uma pesquisa em determinada coluna, como no exemplo: `$contatos = SiteContato::where('mensagem', 'like', '%:)')->get();`. **Lembrar de incluir o(s) %!**

<h2 id="topico25">25. Eloquent - Selecionando registros com whereIn() e whereNotIn()</h2>

- inserir as querys no Workbench:

~~~sql

insert into site_contatos(nome, telefone, email, motivo_contato, mensagem)values('Rosa', '(33) 92222-3333', 'rosa@contato.com.br', 1, 'Quando custa essa aplicação?');

insert into site_contatos(nome, telefone, email, motivo_contato, mensagem)values('André', '(88) 95555-6666', 'andre@contato.com.br', 2, 'Parabéns pela ferramenta, estou obtendo ótimos resultados!');

~~~

- os **métodos whereIn() e whereNotIn()** esperam dois parâmetros:
    - 1. campo a ser comparado por igualdade (no caso de whereIn) ou diferença (no caso de whereNotIn).
    - 2. conjunto de parâmetros.
- é possível passar quantos parâmetros forem necessários, basta separar os parâmetros por vírgula.
- pode ser utilizado para números, datas ou strings.
- na linha de comando:

~~~shell
use \App\Models\SiteContato;
$contatos = SiteContato::whereIn('motivo_contato', [1, 3])->get();
$contatos = SiteContato::whereNotIn('motivo_contato', [1, 3])->get();
~~~

> In e NotIn suportam comparações com valores numéricos, strings e datas.

<h2 id="topico26">26. Eloquent - Selecionando registros com whereBetween() e whereNotBetween()</h2>

- enquanto o `método whereIn()` realiza uma **comparação por igualdade** com um conjunto de valores encaminhados por array, o `método whereBetween()` realiza a **comparação com base em um intervalo**.
- pode ser utilizado tanto para números quanto para datas.
- exemplo:

~~~shell
$contatos = SiteContato::whereBetween('id', [3, 6])->get();
$contatos = SiteContato::whereNotBetween('id', [3, 6])->get();
~~~

<h2 id="topico27">27. Eloquent - Selecionando registros com dois ou mais Wheres</h2>

- permite conectar duas ou mais operações de comparação através do **operador lógico and**.

~~~shell
$contatos = SiteContato::where('nome', '<>', 'Fernando')->whereIn('motivo_contato', [1, 2])->whereBetween('created_at', ['2026-07-30 13:12:27', '2026-07-30 13:23:02'])->get();
~~~

<h2 id="topico28">28. Eloquent - Selecionando registros com orWhere()</h2>

- permite conectar duas ou mais operações de comparação através do **operador lógico or**.

~~~shell
$contatos = SiteContato::where('nome', '<>', 'Fernando')->orWhereIn('motivo_contato', [1, 2])->orWhereBetween('created_at', ['2026-07-30 13:12:27', '2026-07-30 13:23:02'])->get();
~~~
