~~~php
<?php

namespace App\Http\Controllers;

use Illuminate\Http\Request;
use App\Models\Fornecedor;

class FornecedoresController extends Controller
{
    public function index() {
        return view('app.fornecedor.index');
    }

    public function listar() {
        return view('app.fornecedor.listar');
    }

    public function adicionar(Request $request) {

        $mensagem = '';

        if($request->input('_token') != '') {
            // validação dos dados
            $regras = [
                'nome' => 'required|min:3|max:40',
                'site' => 'required',
                'uf' => 'required|min:2|max:2',
                'email' => 'email'
            ];

            // configuração das mensagens de feedback de controle
            $feedback = [
                'required' => 'O campo :attribute deve ser preenchido!',
                'nome.min' => 'O campo nome deve ter no mínimo 3 caracteres!',
                'nome.max' => 'O campo nome deve ter no máximo 40 caracteres!',
                'uf.min' => 'O campo UF deve ter 2 caracteres!',
                'uf.max' => 'O campo UF deve ter 2 caracteres!',
                'email.email' => 'O campo e-mail não foi preenchido corretamente!'
            ];

            // aplicação da validação
            $request->validate($regras, $feedback);

            $fornecedor = new Fornecedor();
            $fornecedor->create($request->all());

            // mensagem de sucesso
            $mensagem = 'Cadastro realizado com sucesso!';
            };


        return view('app.fornecedor.adicionar', ['mensagem' => $mensagem]);
    }
}
~~~

<h2 id="topico6">6. Paginação de registros - Métodos count(), total(), firstItem() e lastItem()</h2>

- na documentação do Laravel, em [Pagination](https://laravel.com/docs/13.x/pagination) > [Cursor Paginator Instance Methods](https://laravel.com/docs/13.x/pagination#cursor-paginator-instance-methods), há uma relação de métodos e suas funcionalidades.

- em `resources/views/app/fornecedor/listar.blade.php`:

### a) $paginator->count():

- exibe o número total de registros da página atual.

~~~php
{{ $fornecedores->appends($request)->links() }}
<br>
{{ $fornecedores->count() }} - Total de registros por página
~~~

### b) $paginator->total():

- exibe o número total de registros da consulta.

~~~php
{{ $fornecedores->total() }} - Total de registros da consulta
~~~

### c) $paginator->firstItem():

- retorna o número do primeiro registro da página (não tem relação com o id, e sim com o número do registro dentro da relação de registros possíveis).

~~~php
{{ $fornecedores->firstItem() }} - Número do primeiro registro da página
~~~

### d) $paginator->lastItem():

- retorna o número do último registro da página.

~~~php
{{ $fornecedores->lastItem() }} - Número do último registro da página
~~~

> Exemplo de aplicação:

~~~php
Exibindo {{ $fornecedores->count() }} fornecedores de {{ $fornecedores->total() }} (de {{ $fornecedores->firstItem() }} a {{ $fornecedores->lastItem() }}).
~~~

> Lembrar que o nosso modelo implementa o `SoftDelete`; ou seja: na prática, lá no BD, estamos apenas atribuindo a data de remoção dos registros (coluna deleted_at). Caso a intenção seja de fato remover esses registros, utilizar a instrução `Fornecedor::find($id)->forceDelete();`.

<h2 id="topico21">21. Relacionamentos 1x1, 1xN e NxN com Eloquent ORM</h2>

- relacionamentos:
    - **1 para 1**:
        - a tabela de maior importância tem sua primary key enviada para a tabela de menor importência no relacionamento.
        - aplicação da constraint unique, que garante a restrição de que um registro na tabela que receberá a chave estrangeira, associe essa chave a um único registro dessa respectiva tabela.
    - **1 para N**:
        - a tabela de maior importância tem sua primary key enviada para a tabela de menor importência no relacionamento.
        - não possui constraint de unicidade (unique) - a pk da primeira tabela pode se repetir para n registros na segunda tabela.
    - **N para N**:
        - requer uma tabela auxiliar, que vai receber como chave estrangeira a chave primária de cada uma das tabelas desse relacionamento.

<h2 id="topico29">29. Extra - Lazy Loading vs Eager Loading parte 1</h2>

- há duas maneiras diferentes de o Eloquent ORM fazer o carregamento dos registros relacionados:
    - **Lazy Loading** (carregamento "lento"): 
        - forma de carregamento padrão.
        - as informações relacionadas dos registros, estabelecidas pelos métodos, são carregados apenas quando o método é chamado.
        - se tentar acessar o atributo de um relacionamento antes de executar o método, não teremos acesso aos campos relativos ao registro daquele relacionamento.
    - **Eager Loading** (carregamento "ansioso"):
        - no Controller, podemos executar o `método with()`, incluindo o método e outros relacionamentos como parâmetros do Model, os quais serão previamente carregados.

- em `app/Http/Controllers/ProdutoController.php`:

~~~php
$produtos = Item::with(['itemDetalhe'])->paginate(10);
// eager loading de itemDetalhe, 
// referente ao método hasOne de Item.php:

/*
public function itemDetalhe() {
    return $this->hasOne('App\Models\ItemDetalhe', 'produto_id', 'id');
}
*/
~~~

<h2 id="topico31">31. Eloquent ORM 1 para N - Criando o relacionamento entre Fornecedor e Produto</h2>

- neste cenário, um fornecedor estará relacionado a N produtos.
- realizar o desenvolvimento incremental das tabelas, implementando esse relacionamento entre produtos e fornecedores; nesse caso, `a chave primária da tabela fornecedores precisa viajar como chave estrangeira para a tabela produtos`.
- nesse momento, a tabela produtos não possui nenhuma coluna para receber a chave estrangeira de fornecedores; portanto, criaremos a migration que fará esse desenvolvimento inclemental. **Na linha de comando, executar**:

~~~
php artisan make:migration alter_produtos_relacionamento_fornecedores
~~~

- na `migration alter_produtos_relacionamento_fornecedores`:

~~~php
public function up(): void
{
    // Criando coluna em PRODUTOS que vai receber fk de FORNECEDORES
    Schema::table('produtos', function(Blueprint $table) {
        $table->unsignedBigInteger('fornecedor_id')->after('id');
        $table->foreign('fornecedor_id')->references('id')->on('fornecedores');
    });
}
~~~

- caso não haja registros nas tabelas, o comando acima funcionará (caso seja a primeira execução das migrations, por exemplo); porém, neste caso, se executarmos desta forma, truncará a tabela, pois será atribuído o valor "0" ao campo fornecedor_id, sendo que não há nenhum fornecedor de id 0 na tabela fornecedores.
- para não ter que apagar todos os registros da tabela produtos, vamos utilizar um comando que insere um registro de fornecedor padrão para estabelecer o relacionamento nos campos já existentes; logo, na `migration alter_produtos_relacionamento_fornecedores`:

~~~php
return new class extends Migration
{

    public function up(): void
    {
        // Criando coluna em PRODUTOS que vai receber fk de FORNECEDORES
        Schema::table('produtos', function(Blueprint $table) {
            
            // Insere um registro de fornecedor para estabelecer o relacionamento
            $fornecedor_id = DB::table('fornecedores')->insertGetId([
                'nome' => 'Fornecedor Padrão SG',
                'site' => 'fornecedorpadraosg.com.br',
                'uf' => 'SP',
                'email' => 'contato@fornecedorpadraosg.com.br'
            ]);

            $table->unsignedBigInteger('fornecedor_id')->default($fornecedor_id)->after('id');
            $table->foreign('fornecedor_id')->references('id')->on('fornecedores');
        });
    }

    /**
     * Reverse the migrations.
     */
    public function down(): void
    {
        Schema::table('produtos', function(Blueprint $table) {
            $table->dropForeign('produtos_fornecedor_id_foreign');
            $table->dropColumn('fornecedor_id');
        });
    }
};
~~~

- executar o comando `php artisan migrate`.

<h2 id="topico36">36. Eloquent N para N - Implementando os requisitos para o relacionamento</h2>

- para viabilizar o estudo desse relacionamento, precisamos viabilizar os requisitos técnicos: criaremos 3 models (Cliente, Pedido e PedidoProduto), e cada model terá uma tabela associada no banco de dados (clientes, pedidos e pedido_produtos).
- a ideia desse relacionamento é permitir, através da tabela pedido_produtos, que haja um relacionamento em que 1 pedido pode estar relacionado a N produtos, e 1 produto possa estar relacionado a N pedidos (ou seja, um **relacionamento de muitos para muitos entre pedidos e produtos**)!

- inicialmente, criaremos os 3 modelos; na linha de comando:

~~~
php artisan make:model Cliente
php artisan make:model Pedido
php artisan make:model PedidoProduto
php artisan make:migration create_clientes_pedidos_produtos
~~~

- o ideal, para que o Laravel identifique a padronização na nomenclatura, é manter a tabela no padrão "pedido_produtos"; porém, para fins didáticos, o prof a chamou de "pedidos_produtos" - e, para que ela seja identificada pelo Laravel, devemos adicionar a instrução no model `app/Models/PedidoProduto.php`:

~~~php
class PedidoProduto extends Model
~~~
